🤖 CAMROBOT — PORT REPORT

Repo: github.com/abourdim/wdiy_esp32_cam_robot  |  Package: Codes/4_CamRobot  |  Ported from abourdim/video-car v1.6.1  |  2026-08-27  |  See also README · ports guide

Summary

This is not a feature report. Every feature in this firmware already existed in VideoCar, which does the same job on the keyestudio KS5017 chassis. What this documents is a port: the same web app moved onto the esp32_cam_plugin_robot carrier board (WORKSHOP-DIY ID_04, 16/10/2023), and the specific places where that board would not accept it unchanged.

The pin map below was read out of esp32_cam_plugin_robot.kicad_pcb's netlist rather than assumed from the module. That matters, because two of the three breaking differences are pins that the AI-Thinker module and the carrier both have opinions about, and neither opinion is visible from the other end.

Testing status. Both firmware environments compile clean, and the control page's script block parses and was exercised in a browser against a stubbed fetch — see Verification below for exactly what that covered and what it did not. None of it has been flashed to the real board. Put the robot on blocks the first time.

What the hardware forced

No reverse breaking

The keyestudio car drove an I2C motor controller at 0x30 that took a PWM byte and a direction byte per side. This board has neither the chip nor the direction bit: each motor is one low-side N-MOSFET (Q1/Q2, 2N7002) with its gate on a GPIO, the motor between the screw terminal and the battery rail, and a 1N4007 across it for flyback. One switch per motor is one degree of freedom per motor, and no H-bridge means no way to run a wheel backwards.

That single fact reaches further than anything else in this port:

  • Car_backwards() is kept, so the file still presents the same five verbs, but it can only stop — and says so on serial rather than silently doing nothing.
  • /control?var=car&val=2 answers 200 and stops. Not an error, because a browser holding a cached older control page can still send it, and a robot that sits still beats one logging failures at 10 Hz.
  • Turns became a forward pivot around the undriven wheel instead of a spin on the spot, so the robot swings through a far wider arc. This is why TURN_SPEED_PERCENT matters more here than it did there.
  • /joystick's y is clamped to 0. The arcade mixing is otherwise untouched: the lower clamp on the mixed wheel values moved from -100 to 0, and forward-only steering falls out of that one edit rather than needing a special case.
  • The D-pad's Back button became Stop, which the page could not previously ask for outright. The Down arrow key was repurposed the same way rather than left dead.
  • FOLLOW_MAX_REV and CHASE_MAX_REV became named zeros, so Follow-me and Colour chase stop and wait when a target closes in rather than backing off. They are named rather than deleted so a chassis that grows an H-bridge later has one number to change.

The headlight moved off GPIO12, because GPIO12 is a wheel breaking

VideoCar's lamp was a plain white LED driven with analogWrite(12, level). On this board GPIO12 is motor 2's gate, so that call spins a wheel. The light is now D3, a single TX1812DB addressable pixel on GPIO4, behind src/lights.h. The Lights slider keeps its 0–255 range and its NVS key, so a saved setting carries across unchanged and still means the same thing.

GPIO4 is shared: on an AI-Thinker module it is also the gate of the onboard flash LED. That is harmless only because lightsSet() refuses to resend a level that has not changed — one pixel frame is about 30 µs and invisible, but a continuous refresh would leave that very bright LED glowing at the average duty, which reads as a hardware fault.

GPIO12 is also MTDI, the flash-voltage strapping pin. R2's 10k pulldown is the only reason it is usable as an output here at all; without it the module boots expecting 1.8V flash and does not boot.

PSRAM and the motion sensor want the same pin build-time choice

The carrier provides for an HC-SR501 (soldered at U2, or plugged into J6) whose output reaches the ESP32 through Q3 as a common-emitter inverter into GPIO16 — so motion reads low, and since R3 is in series rather than to a rail, the pin needs INPUT_PULLUP or it reads noise.

GPIO16 is also the PSRAM chip-select on this module. They cannot both have it, so it is decided at build time: the default keeps PSRAM (two QVGA buffers, no sensor, /status reports "pir":-1), and env:esp32cam-pir takes the sensor instead and falls back to a single DRAM frame buffer with QVGA as a hard ceiling. Both environments are built, so neither path rots.

src/pir.h carries an #error for the half-made version of that change, because a build that kept PSRAM and read GPIO16 anyway would report "motion" every time the cache missed — a robot that works, streams, and lies.

The OLED got its bus to itself improvement

This is the one place the port came out better than its source. On the keyestudio car the screen shares GPIO14/13 with the motor controller, which costs a mutex, dropped frames, a rule against drawing while driving, and — on the micro:bit robots in the same family — the risk that an unplugged screen takes the motors down with it.

Here the motors are two PWM pins and the screen has GPIO14/15 entirely to itself. The mutex is gone, oledPush() no longer drops frames, and a missing screen costs nothing but the screen. The "don't draw while driving" rule was kept, but only for the second of its two reasons: nobody watches the eyes of a robot that is driving away from them.

Neither pin is broken out on the carrier, so a screen has to be soldered to the module's own header. Most builds will not have one, which is why the firmware probes at boot and carries on silently. The boot self-test lost its "Driver 0x30" line — there is no chip left to ask — and spends it on the motion sensor instead, rather than printing a reassuring "ok" that tests nothing.

Things the board simply does not have documented

  • No microSD. GPIO 2, 4, 12, 13, 14 and 15 are the module's SD pins; this board spends 12, 13 and 4 on the motors and the pixel. Nothing to fix.
  • No auto-reset, no boot button. J3 is a bare 5V/RX/TX/GND header and GPIO0 goes to the module and nowhere else, so the first flash means jumpering GPIO0 to GND by hand. This is why OTA got its own menu entry in launch.sh.
  • USB-C is power only. J7's CC1/CC2 are unpopulated, so it takes 5V from an A-to-C cable or a dumb supply, not from a charger expecting to negotiate.
  • Two supplies. +5V (USB-C) runs the logic; VCC (J5) is the motor rail. A robot on USB alone boots and streams and cannot move. J4 bridges them if that is what you want.

What carried over untouched

Everything not listed above, which is most of it: the MJPEG stream on port 81 and the two-server split, /capture, the 500 ms connection-loss failsafe, the sticky viewfinder and collapsible panels, the whole browser-side vision suite, the IndexedDB offline model cache, the autonomy arbiter, snapshot and recording, the build stamp and its PlatformIO pre-build hook, POST /update, ArduinoOTA, the WiFiManager captive portal, and the English/French/Arabic translations.

The three lesson sketches carried over in shape rather than in code, because both things they demonstrate moved: 1_Blink and 2_breathing_light now drive the RGB pixel (an addressable LED has no analog input to write, so the fade is done by scaling the colour), and 3_motor drives two MOSFETs instead of an I2C controller.

Corrections made during the port

VideoCar's PSRAM comment was wrong fixed

firmware/4_videocar/platformio.ini states that PlatformIO's generic esp32cam board definition does not set the PSRAM flags for you. It does: esp32cam.json carries -DBOARD_HAS_PSRAM -mfix-esp32-psram-cache-issue in its own extra_flags. Deleting the -D from build_flags therefore changes nothing, because build_flags cannot remove what extra_flags added — it has to be undefined with -UBOARD_HAS_PSRAM.

Found the hard way: the motion-sensor build hit the #error in pir.h despite the flag having been removed. The guard did its job on its first outing.

The boot flash left the headlight at full brightness fixed

VideoCar's ready-indicator loop ends on analogWrite(LED, 255), discarding the Lights level it restored from NVS moments earlier. Easy to miss on a dim white LED and impossible to miss on a 5V RGB pixel. The saved level is now put back after the flash. The ready blink is also green rather than white, so it cannot be mistaken for the headlight coming on.

pio run -t upload tried every environment fixed

With esp32cam, esp32cam-ota and esp32cam-pir all defined and no default_envs, a bare pio run -t upload walks all three and tries to flash the robot over USB, then over the network with no address, then again with the sensor build. [platformio] default_envs = esp32cam pins the default; the other two are reached with -e, which is what launch.sh's OTA and "build a specific environment" options pass.

Verification

Compiled. All four PlatformIO projects build clean against espressif32@6.5.0. 4_camrobot at 62.3% of the 1.9MB OTA partition (1,224,865 bytes) with PSRAM, 61.7% in the sensor build.

Parsed. The control page's single 114 KB inline script block was extracted and checked with node --check.

Exercised. The page was served locally and driven with window.fetch stubbed, recording what the firmware would have received: idle → val=5, ArrowUp → val=1, ArrowLeft → val=3, ArrowDown → val=5 (cancelling a held Forward), Stop button → val=5. The #backward element is gone and #stopbtn is in its grid slot.

Not done. Nothing has been flashed. Nothing has driven a real motor, lit a real pixel, or read a real sensor. In particular the TX1812's byte order is assumed to be GRB (switch NEO_GRB to NEO_RGB in lights.h if red and green swap), 20 kHz motor PWM through a 3.3V gate drive on a 2N7002 has not been checked against real motors and real stiction, and the inverted PIR path has never seen a person walk past it.

Known limitations / open items

  • Untested on hardware. The largest item on this list by some distance.
  • No reverse, and no way to add one in software. A robot that overshoots has to drive round rather than back up. Autonomous modes inherit this and are meaningfully worse for it — Follow-me in particular can only stop when a target closes in.
  • No braking either. Zero duty is a coast: the MOSFET stops conducting and the motor freewheels. There is no way to short the windings, so the robot always rolls slightly past where you let go.
  • Turn radius. A forward pivot needs roughly twice the floor space of the spin the keyestudio car did. Anything tuned on that chassis — the line follower especially — may need retuning here.
  • PSRAM or motion, never both. Not fixable without cutting a trace.
  • No authentication on any endpoint. Inherited, and unchanged: anyone on the same WiFi can drive the robot and watch the camera. Fine on an isolated AP, worth thinking about on a home router.
  • The vision features still need internet on first use, which the default AP does not have. The IndexedDB cache means once is enough.
