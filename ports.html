🤖 CAMROBOT — PORTS 80 & 81, STEP BY STEP

A beginner's guide to talking to the robot directly  |  Repo: github.com/abourdim/wdiy_esp32_cam_robot  |  See also README · change report

The robot runs two separate web servers at the same time. This guide explains what each one is for, then walks you through using both — first in a browser, then from the command line. No prior knowledge of HTTP assumed. Nothing here requires editing or recompiling the firmware.

This robot has no reverse. Each motor has a single low-side MOSFET and no H-bridge, so a wheel can be driven or not driven and nothing else. Two things below follow from that, and they are the only places this guide differs from the same document on the car this was ported from: /control?var=robot&val=2 stops instead of reversing, and /joystick's y is clamped to 0–100 rather than −100–100.

The 30-second version

PortWhat lives thereOpen it with
80 Control server. The web page you drive from, plus every command and setting, plus single still photos. http://192.168.4.1/
81 Stream server. One job only: the continuous live video feed. http://192.168.4.1:81/stream

When you leave the port off a URL, your browser assumes 80. That is why the control page needs no port and the stream always does.

Why two servers instead of one?

This looks like over-engineering until you know how the video works. The stream is MJPEG — motion JPEG. The robot does not send a video file. It opens one HTTP response and then never closes it, pushing out an endless run of JPEG stills separated by a marker line, and the browser paints each one as it arrives.

That means a streaming connection stays open forever. The tiny web server on the ESP32 handles a limited number of connections, and a request that never finishes occupies its slot indefinitely. If the stream and the controls shared one server, the stream could starve the controls — and a robot that will not accept a stop command because it is busy sending video is a genuinely dangerous robot.

So video gets its own server, on its own port, with its own connection pool. Steering commands never queue behind picture data.

   Your phone or laptop
            │
            ├──────────────▶  port 80   control server
            │                 ├─ /          the drive page
            │                 ├─ /status    what the robot is doing
            │                 ├─ /control   drive + settings
            │                 ├─ /joystick  proportional drive
            │                 └─ /capture   one still photo
            │
            └──────────────▶  port 81   stream server
                              └─ /stream    live video, never ends

Before you start

  • A robot with this firmware flashed. Check the footer of the control page: it shows the version, build time and git commit. If it says nogit and you built with PlatformIO, something is off.
  • A phone or laptop on the same network as the robot.
  • Optional, for the command-line steps: curl. It ships with macOS and most Linux systems, and with Windows 10 and later. Everything can also be done from a browser address bar if you prefer.
Put the robot on blocks before any of the driving steps. A book under each side, wheels clear of the desk. You are about to send it commands by hand, and it is very easy to send “forward” and then go looking for the stop command while it drives off the table.

Walkthrough

1

Get on the same network as the robot

Default (access point mode). The robot makes its own WiFi network. On your phone or laptop, join:

network:  wdiy1
password: 88888888

The robot is then always at 192.168.4.1. It has no internet connection — it is a network of exactly two devices, you and the robot.

If you changed the firmware to station mode (ap = 0), the robot joins your home router instead and the router decides its address. Plug it into USB, open a serial monitor at 115200 baud, and watch the boot messages:

CamRobot v1.0.0  |  built Aug 27 2026 09:14:22  |  a1b2c3d
Starting web server on port: '80'
Starting stream server on port: '81'
Camera Ready! Use 'http://192.168.1.42' to connect

Use whatever address it prints, in place of 192.168.4.1 everywhere below.

You should see: your device connected to the network. On a phone, expect a warning that the network has no internet. That is correct in AP mode — do not let the phone "helpfully" switch back to mobile data.
2

Open the control page — this is port 80

In a browser, go to:

http://192.168.4.1/

No port number. The browser fills in 80 silently. This single page is what the whole project is for: live video, a D-pad, a joystick, sliders and the vision features.

You should see: the dark control page, live video within a second or two, and a build stamp in the footer.
Blank page or a spinner forever? Check you typed http:// and not https://. The robot speaks plain HTTP only, and some browsers now try HTTPS first and give up quietly.
3

Watch the raw video — this is port 81

Open a new browser tab and go to:

http://192.168.4.1:81/stream

The :81 is the whole point of this step. You get the video on its own, filling the window, with no page around it. This is exactly the same data the control page shows — the page simply wraps it in an <img> tag.

Seeing it bare is the fastest way to answer "is the camera working, or is the page broken?" If this tab shows video, the camera and both servers are fine and any problem is in the page.

You should see: live video and a tab spinner that never stops. That is correct. The response genuinely never finishes.
Close this tab before going back to driving. The camera has a limited number of frame buffers, and every open stream is another consumer. Two viewers at once will make both stutter.
4

Take a single photo

Still port 80. In a browser:

http://192.168.4.1/capture

One JPEG, taken the moment you asked, then the connection closes normally. This is the opposite of the stream: one picture, one request, done.

From a terminal, save it to a file:

# save one frame as shot.jpg
curl http://192.168.4.1/capture -o shot.jpg
You should see: a single still image in the browser, or a shot.jpg you can open.
5

Ask the robot what it is doing

Every setting the robot holds is readable in one request:

http://192.168.4.1/status

You get JSON — a machine-readable summary:

{"framesize":5,"quality":16,"vflip":1,"hmirror":1,
 "speed":8,"trim":0,"flash":10,
 "version":"1.0.0","build":"Aug 27 2026 09:14:22","gitrev":"a1b2c3d",
 "oled":0,"pir":-1,"reverse":0}

The last three are this board's. oled says whether a screen answered at 0x3C during boot. pir is 1 for motion, 0 for quiet, and -1 when the motion sensor is not compiled into this build — which is the default, because the sensor and the camera's PSRAM want the same pin. reverse is 0 and always will be; it is there so a page or a script can find out without having to be told.

This is the endpoint the control page itself calls on load, to restore your sliders, and every two seconds after that as a connection check. It is also the polite way for your own scripts to find out what the robot is set to before changing anything.

You should see: a line of JSON. Browsers usually pretty-print it or offer to download it — either is fine.
6

Change a setting by hand

Settings use one endpoint with two parameters: var (what to change) and val (the new value). Try the headlight, which is harmless and obvious:

# half brightness
http://192.168.4.1/control?var=flash&val=128

# off again
http://192.168.4.1/control?var=flash&val=0

Paste those into the address bar. The page will go blank — that is normal, the robot replies with an empty "OK". Look at the robot, not the screen.

The same from a terminal. Note the quotes: & means something special to most shells, so the URL must be quoted.

curl "http://192.168.4.1/control?var=flash&val=128"
You should see: the RGB pixel on the front of the robot light up white, then go off. Settings are saved to the robot's flash, so they survive a reboot.
Full brightness (255) on a 5V pixel is genuinely bright. Fine in bursts, not for long periods.
The onboard flash LED may blink once as you do this. Not a fault: the pixel's data line is GPIO4, which on an AI-Thinker module is also the gate of that very bright white LED next to the lens. One pixel update is about 30 microseconds of traffic on it.
7

Drive it — and meet the failsafe

Driving uses the same endpoint with var=car:

val=1  forward     val=4  turn right
val=2  (no reverse -- stops)
val=3  turn left     val=5  stop

val=2 answers 200 OK and stops the wheels. It is not an error because a browser holding a cached copy of an older control page can still send it, and a robot that sits still is a better answer than one logging failures ten times a second. The current control page has no Back button to send it with.

Turns are a forward pivot, not a spin on the spot: one wheel is driven and the other coasts, so the robot swings round the stationary wheel and needs roughly twice the floor space the keyestudio car it was ported from needed.

Wheels off the ground? Try it:

curl "http://192.168.4.1/control?var=car&val=1"

The wheels will turn for about half a second and stop. Nothing is broken. This is the safety failsafe, and it is the single most important thing to understand about driving this robot over HTTP.

The firmware stops the motors if 500 ms pass with no new command. Without that, a robot told "forward" would keep going forever if your WiFi dropped, your battery died, or you simply closed the laptop. There is no other way for it to know you are still there.

So one command is not an instruction, it is a lease. To keep moving, keep renewing it. That is exactly what the control page does — it re-sends the current command every 100 ms, well inside the 500 ms window.

To drive forward for three seconds from a terminal:

# macOS / Linux
end=$((SECONDS+3))
while [ $SECONDS -lt $end ]; do
  curl -s "http://192.168.4.1/control?var=car&val=1" > /dev/null
  sleep 0.1
done
curl -s "http://192.168.4.1/control?var=car&val=5" > /dev/null   # stop

The explicit stop at the end is good manners rather than strictly required — the failsafe would stop it half a second later anyway. Send it regardless. Relying on a safety net for ordinary operation is how you end up surprised the one time it does not fire.

You should see: wheels turning for three seconds, then stopping.
If a script gets away from you, close the terminal. The moment commands stop arriving, the robot stops within half a second on its own.
8

Steer smoothly instead of in four directions

/control?var=car only knows four directions and stop. For proportional control — any direction, any speed — use the joystick endpoint:

http://192.168.4.1/joystick?x=0&y=100      full speed ahead
http://192.168.4.1/joystick?x=100&y=0      pivot right
http://192.168.4.1/joystick?x=-50&y=60     forward, curving left
http://192.168.4.1/joystick?x=0&y=-100     clamped to y=0, so: stop
http://192.168.4.1/joystick?x=0&y=0        stop

x is steering and runs -100 to 100 (positive is right). y is throttle and runs 0 to 100 — negative values are clamped to zero rather than rejected, so pulling back does nothing rather than erroring.

The firmware mixes them into left and right wheel speeds the way an arcade cabinet does, and forward-only steering falls out of that mixing rather than being a special case: a wheel whose mixed value would go negative simply stops. That is why x=100&y=0 above is a pivot — one wheel gets 100, the other is clamped to 0.

The same 500 ms failsafe applies, so the same rule holds: repeat it, roughly ten times a second, for as long as you want to move.

You should see: a brief twitch per request — and smooth motion once you send them in a loop.

Full reference — port 80

RequestReturnsNotes
GET /HTML The control page. Sent with Cache-Control: no-store, so you always get the page belonging to the firmware that is actually running.
GET /statusJSON All current settings plus firmware version, build time and git revision.
GET /captureJPEG One still frame at the current resolution and quality.
GET /control?var=…&val=…empty Settings and basic driving. See the table below.
GET /joystick?x=…&y=…empty Proportional driving. x is −100 to 100, y is 0 to 100; out-of-range values are clamped, not rejected.

Values for /control

varvalEffect
robot1–5 1 forward, 2 stops (no reverse), 3 left, 4 right, 5 stop. Subject to the 500 ms failsafe — repeat to keep moving.
speed0–8 Overall speed cap. Multiplied by 31 internally, so 8 means a PWM ceiling of 248 out of 255.
trim−32–32 Corrects a robot that drifts when it should go straight. Negative favours one motor, positive the other. It earns its keep here: two bare MOSFETs driving two unmatched motors off one rail is as open-loop as a robot gets.
flash0–255 Front RGB pixel brightness, as white.
framesize0–6 Resolution. 0 = 96×96, 1 = QQVGA, 2 = QCIF, 3 = HQVGA, 4 = 240×240, 5 = QVGA 320×240 (default), 6 = CIF. Bigger is slower.
quality10–63 JPEG quality, and it runs backwards: lower numbers look better and produce bigger frames.
vflip0 or 1Flip the picture vertically.
hmirror0 or 1Mirror the picture horizontally.
wifichannel1–11 WiFi channel for the robot's own AP (default 11). Reboots the robot — a channel is fixed when the access point starts, so there is no way to move it while it is up. A crowded channel shows up as laggy controls and stuttering video rather than as a dropped connection, so if the robot feels slow, compare 1, 6 and 11 — the three that don't overlap.

Everything except robot is saved to the robot's flash memory and survives a power cycle — including a reflash. If you change a setting and later wonder why a new firmware's default didn't take, this is why: the saved value wins. Check /status for what the robot is actually using. Only robot and /joystick reset the failsafe timer — changing a setting does not count as "I am still here".

Full reference — port 81

RequestReturnsNotes
GET :81/stream multipart/x-mixed-replace Endless JPEG frames. The only endpoint on this port.

If you fetch it with a tool rather than a browser, expect a response that never completes. That is the design, not a hang. The frames are separated by a fixed boundary marker, each with its own Content-Type: image/jpeg and length, and the server sends Access-Control-Allow-Origin: * so a web page on port 80 is allowed to read the pixels — which is how the vision features work.

Putting the video in your own page

The stream is a plain image source. Any browser that can show a JPEG can show it, with no JavaScript at all:

<img src="http://192.168.4.1:81/stream" width="320">

That is the entire trick. The control page does exactly this and then draws boxes on a transparent canvas laid over the top.

If you want to read the pixels — to run your own detection, or grab frames into a canvas — add crossorigin:

<img id="v" src="http://192.168.4.1:81/stream" crossorigin="anonymous">
<script>
  const c = document.createElement('canvas');
  const ctx = c.getContext('2d');
  const img = document.getElementById('v');
  setInterval(() => {
    c.width = img.naturalWidth; c.height = img.naturalHeight;
    ctx.drawImage(img, 0, 0);            // current frame, as pixels
  }, 100);
</script>

Without crossorigin, the browser still shows the video but marks the canvas as "tainted" and refuses to let you read it back — because port 81 counts as a different origin from port 80, even on the same device. The robot sends the header that makes this work.

Things that will trip you up

  • Only one device can join the robot's WiFi. The access point is configured for a single client. If your laptop is connected, your phone cannot be. Worse, an ungraceful disconnect can hold the slot for a minute or two — if you cannot reconnect, wait, or power-cycle the robot.
  • One stream viewer at a time, in practice. Nothing stops you opening two, but they compete for camera buffers and both suffer.
  • There is no password on any of this. Anyone on the network can drive the robot, and every command is a plain URL — so an <img src="…/control?var=car&val=1"> hidden on any web page you happen to open while connected is enough to make it move. Treat the robot's network as untrusted and do not leave it running unattended.
  • & needs quoting in a shell. An unquoted & tells most shells to run the command in the background, so only the first parameter arrives. Always quote the whole URL.
  • Do not write :80 explicitly. Some of the page's JavaScript builds the stream URL from the current address, and an explicit :80 turns into a broken :80:81. Just omit it.
  • Higher resolution is not free. framesize=6 quadruples the data over the same WiFi. If the stream turns into a slideshow, go back to 5.
  • Settings persist, so surprises persist too. If the robot boots with the light on or the picture upside down, that is a saved setting from last time, not a fault.

Quick test script

Checks both servers and reports what it finds. Wheels on blocks — it drives briefly.

#!/bin/bash
CAR=http://192.168.4.1

echo "--- port 80: status ---"
curl -s $CAR/status || echo "NO RESPONSE on port 80"
echo

echo "--- port 80: still photo ---"
curl -s $CAR/capture -o /tmp/shot.jpg && ls -l /tmp/shot.jpg

echo "--- port 81: stream (first 2 seconds) ---"
curl -s --max-time 2 $CAR:81/stream -o /tmp/stream.bin
echo "received $(wc -c < /tmp/stream.bin) bytes of video"

echo "--- drive forward 1s, then stop ---"
end=$((SECONDS+1))
while [ $SECONDS -lt $end ]; do
  curl -s "$CAR/control?var=car&val=1" > /dev/null; sleep 0.1
done
curl -s "$CAR/control?var=car&val=5" > /dev/null
echo "done"
A healthy robot gives you: a line of JSON, a shot.jpg of a few kilobytes, tens of kilobytes of video, and one second of wheel movement. If the JSON arrives but the video does not, the stream server failed to start — check the serial console at boot for both port: '80' and port: '81' lines.
